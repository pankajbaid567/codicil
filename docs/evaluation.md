# Evaluation design

Written before any number was measured. Results are in `docs/results.md`, generated by `make eval`.

## The question
Does the pipeline find the clause that answers a question, rank it high, refuse when nothing answers, and cite only what supports its sentences, in English and in Hinglish, within a free-tier latency budget? And which stages earn their cost?

## Dataset (`eval/questions.jsonl`)
| Slice | Target size | What it tests |
|---|---|---|
| Answerable, single clause | about 120 | Core retrieval and extraction |
| Answerable, multi-clause or comparison | about 20 | Fusion across clauses and entities |
| Unanswerable (near-miss) | about 30 | Abstention. Questions that sound in-scope but the corpus does not answer (for example about rules in documents not ingested) |
| Hinglish / Hindi paraphrases | about 30 | Query normalisation and multilingual retrieval; each is a paraphrase of an answerable question so the gold evidence is shared |
Each record: `id, question, language, slice, answerable, gold_evidence: [{doc_id, quote}], notes, split, provenance`.

**Gold = evidence quotes, not chunk ids.** A retrieved chunk counts as a hit if, after whitespace and case normalisation, it contains the gold quote, or the quote contains most of the chunk (overlap above 0.5). This lets the same dataset score fixed windows, sentence windows and clause chunks fairly. A script verifies that every gold quote exists verbatim in the extracted corpus text, so a typo cannot silently become an impossible question.

**Provenance, stated plainly.** Questions were drafted by an AI assistant reading the extracted clause text; they have not yet been reviewed by the author (see `eval/README.md`). This is author-labelled data, not independent annotation, and the Hinglish slice is written by non-native-speaker conventions. These are limits of the result and are repeated in the README.

**Split.** 50% dev, 50% test, assigned once by hashing the question id; paraphrases follow their source question so a question and its paraphrase never straddle the split. Thresholds (`tau`, fusion weights, BM25 parameters) are tuned on dev only. Test is run once per release.

## Metrics
| Metric | Definition |
|---|---|
| Recall@k (k = 1, 5, 10, 20) | fraction of answerable questions with a gold hit in the top k |
| MRR@10 | mean reciprocal rank of the first gold hit |
| nDCG@10 | binary relevance, log2 discount |
| Evidence coverage | fraction of gold quotes covered by the packed context at the token budget |
| Abstention precision / recall | precision: of abstentions, fraction on unanswerable questions; recall: of unanswerable, fraction abstained |
| Citation support | fraction of returned sentences passing the support check against their cited chunk |
| Extractive answer hit | the returned answer sentences contain the gold quote (extractive mode) |
| Latency | p50 / p95 per stage and total, warm, open-loop at a fixed request rate |
| Memory | peak resident set during the latency run |
All with 95% bootstrap confidence intervals (2,000 resamples over questions). Slices are reported separately; the aggregate is never the only number.

## Ablation plan (each row changes one thing from the full pipeline)
1. BM25 only; 2. dense only; 3. hybrid RRF; 4. hybrid + rerank; 5. fixed-window chunks instead of clause chunks; 6. no contextual header; 7. no parent expansion; 8. no query normalisation (Hinglish slice); 9. no entity boost; 10. embedder A vs B (ADR-007); 11. tau sweep for the abstention curve.
Any stage whose removal does not hurt is flagged for removal.

## Regression gate
`make eval-gate` runs the dev split on **cached vectors** (so CI needs no model download) and fails if recall@10 or nDCG@10 drop by more than 0.02 from the committed baseline, or abstention precision falls below its floor.

## Threats to validity (listed so they are not discovered later)
Small n (CIs will be wide on the unanswerable and Hinglish slices); labels drafted by the same system builder; the near-miss unanswerable questions are my guess at what confuses the pipeline; one corpus and one issuer; lexical support checking can pass a sentence that rearranges true words into a false meaning; LLM-mode answer quality is not measured unless a key is supplied (`make eval-llm`), and no LLM numbers are claimed otherwise; free-tier latency is not a benchmark.
