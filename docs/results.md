## Answer and abstention (extractive mode, e5 profile)

Rule: for English the abstention signal is the cross-encoder's top score (below -0.18 abstain); for Hindi it is the top dense cosine (below 0.84); Hinglish never abstains on a score, because none of the signals tried (dense cosine, cross-encoder score, AUC 0.63 and 0.76 on 22 answerable / 12 unanswerable) had a threshold that kept answerable questions served while catching negatives (the dense rule alone abstained on 33% of answerable Hinglish test questions and caught none of the negatives). -0.18 was chosen on the dev split only (highest recall with precision at least 0.9) and then applied unchanged to test. The first version of this section used the dense cosine for every language and missed the PRD targets on test (precision 0.71, recall 0.31); that threshold is kept for non-English only. Note that the English test questions had already been looked at once under the old rule, so this is a second look at that split, though no threshold was fitted on it.

|---|---|---|---|---|---|
| English | dev | 14 | 0.93 | 1.00 | 97% |
| English | test | 16 | 1.00 | 0.81 | 100% |
| Hinglish | dev | 6 | 0.00 | 0.00 | 90% |
| Hinglish | test | 6 | 0.00 | 0.00 | 67% |
| Hindi | dev | 4 | 1.00 | 0.75 | 100% |
| Hindi | test | 4 | 0.67 | 0.50 | 75% |

Extractive answer contains the gold sentence in 73% of served English test questions. The PRD targets (precision 0.8, recall 0.7) are met for English on test. They are **not** met for Hinglish (no abstention) or Hindi (4 unanswerable questions per split, so any number is anecdotal). The language detector tags 5 of the 34 Hinglish questions as English, so those are routed to the English rule (and the English reranker), which is why the Hinglish answerable-served rate is below 100% even though Hinglish has no score threshold; improving that detector is open work. A Hinglish question the Directions do not cover will therefore usually get the closest clause as its answer; the UI shows the cited clause so the reader can see it does not answer the question.

Unanswerable Hinglish and Hindi questions are translations of English ones (same split as their source). The unanswerable questions were drafted by an AI assistant and checked against the retrieved passages, not independently reviewed. Extractive sentence selection remains the weakest stage: the retrieved passage usually contains the answer but the chosen sentence contains it less often, which is why the UI shows the full cited clause.

## Latency and memory (local, Apple M3, 8 GB, closed loop, one client)

In-process pipeline time over the 148 eval questions: p50 324 ms, p95 446 ms. Most of it is the cross-encoder (20 passages). RSS is flat under load once ONNX Runtime's arena uses `kSameAsRequested` (the default arena grew from 400 to 670 MB on the same run). The first deployment attempt on a 512 MB host was killed for exceeding memory at startup (about 568 MB peak): the Hugging Face tokenizer for multilingual-e5 alone keeps about 290 MB resident, so the service uses the original SentencePiece model instead (same token ids on every chunk and question; ADR-023). The latency table above was measured before that swap; the tokenizer itself costs 0.006 ms per query against 0.1 ms for the Hugging Face one, so latency is not expected to rise, but it has not been re-measured on a quiet machine, and memory after the swap is the 402 MB peak (maximum resident, `/usr/bin/time -l`), not the 445 MB shown. Nothing here is a claim about the free hosting tier.
